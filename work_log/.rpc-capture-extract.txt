Reader: prolinks_poc.capture.pcap.read_capture (Ethernet/IPv4/UDP, with IP-fragment
reassembly -- essential, because 8k+ NFS replies arrive as 6-20 fragments).

IMPORTANT METHOD NOTE: filtering on ports {111, 2049, 48276} alone finds only 16,799
datagrams and misses ~85% of the RPC traffic. Our own NFS/MOUNT server binds EPHEMERAL
ports (it registers them with its portmapper), so a deck talking to us uses ports like
50978/63525/61886. The scan below is therefore CONTENT-based: every UDP payload >= 24
bytes is RPC-decoded and kept if it is a CALL with rpcvers==2 and prog in
{100000,100003,100005}, or a REPLY whose xid matches a call already seen in that file.
That yields 113,900 datagrams: 56,966 calls and 56,934 replies.

The journals (captures/journals/*/journal.jsonl, records with 'hex' + 'local_port')
were also decoded: 1,796 RPC records, ALL of which are duplicates of datagrams already
present in the pcaps (same sessions, logged by our own tool). They contribute nothing new.

HEADLINE RESULTS (details and byte evidence in the numbered sections)
----------------------------------------------------------------------------------------------------
  * REQUESTED ITEMS 9 (STATFS), 10 (READDIR) and NFS NULL: NOT PRESENT IN CORPUS.
    A CDJ only ever issues GETPORT, MNT, UMNT, LOOKUP, GETATTR and READ. Nine
    (prog,vers,proc) triples exist in the whole corpus and a deck uses six of them.
  * MOUNT EXPORT does exist (3 calls) but F37 holds: no CDJ ever calls it. All 3 are
    computer-originated. The replies are real Pioneer bytes and are quoted.
  * The mount path is UTF-16LE with a trailing slash: '/C/' = 2f0043002f00 (USB),
    '/B/' = 2f0042002f00 (SD). '/C/EXPORT' appears only in dysentery's older capture.
  * F28 CONFIRMED, and more strongly than documented: the 12-byte truncation also
    happens DECK-TO-DECK, so it is Pioneer firmware talking to Pioneer firmware. The
    12 surviving bytes are three 32-bit ids [self, parent, mount-root].
  * CORRECTION TO C8: the AUTH_UNIX stamp is NOT a nonce. It is a DETERMINISTIC
    function of the xid -- 56,102 Pioneer-originated calls, 9,947 recurring xids,
    ZERO disagreements, and dysentery's 2016 capture off different hardware produces
    the identical stamp for xids 1..9. 0x967b8703 is simply entry #1. A 32-entry
    lookup table of the real sequence is given in section 13.
  * NEW: in a CDJ's READ reply the fattr is ALL ZEROS except fileid (7884/7884). Its
    LOOKUP and GETATTR replies carry a full, correct fattr. Do not read size from a
    READ reply.
  * REFINEMENT OF F19: 8192 is not the ceiling. A deck asks its peer for 9408 most
    often, and up to 28584 bytes in a single NFSv2 UDP READ, answered in full as a
    28,656-byte datagram (~20 IP fragments).
  * A CDJ's file mode is 0o100000 (no permission bits) and a directory's is 0o040666;
    all timestamps are the constant 1672531200 (2023-01-01T00:00:00Z).

  CONCLUSION, superseding C8:
    * The stamp is NOT a nonce and NOT random. It is a fixed sequence indexed by the
      call number since boot, identical on every Pioneer device tested.
    * research/06 was half right: 0x967b8703 IS a constant -- entry 1 of the sequence.

      first call, which is why prolink-connect works.
    * C8's practical advice still stands and is now better grounded: a SERVER must never
      validate the stamp, and a CLIENT may send anything. But a test CAN assert the exact
      stamp for a given call index, and a capture's stamp tells you how many RPC calls the
      deck has made since it was powered on.

    03 01 2d 00   00 00 1b 58   00 00 00 00   03 03 01 00   00 00 01 62

self-describing in its first 12 bytes. Bytes 12..31 are scratch space the client owns.

READ INTERPRETATION -- this refines F19:
  * 8192 is NOT the ceiling. A CDJ asks for 9408 and, for the first read of a file, values
    up to 28584. Its peer answers in full: a single 28,656-byte UDP datagram.
  * 2048 dominates overall (41,630 / 52,480 CDJ reads) but that is almost entirely traffic
    against OUR server, whose replies the deck evidently probes down to a safe size.
  * Deck-to-deck (pure Pioneer, 7043 reads) the picture is different: 9408 is the modal value
    (5,097), then 8192 (1,283), then 2048 (264).
  * `totalcount` is 0 in every single one of the 53,322 READ calls.
  * offset is a plain byte offset and IS NOT always block-aligned: a track read typically
    starts at offset 44 (past a WAV/ID3-ish header) and then advances by the count.
  * A real deck therefore relies on IP fragmentation as a matter of course.

CONFIRMED CONSTANTS in a real CDJ's LOOKUP and GETATTR fattr (401 samples, no exceptions):
  uid       = 0
  gid       = 0
  nlink     = 1
  blocksize = 512
  rdev      = 1          <-- NOT 0. A regular file with rdev 1.
  fsid      = 2          <-- the same 2 for both the /C/ and /B/ mounts
  atime = mtime = ctime = 1672531200.000000 = 2023-01-01T00:00:00Z, a hard-coded epoch.
                          The deck never reports a real file time.
  mode      = two values only:
                0o100000 (0x8000) = S_IFREG with ZERO permission bits, for a file
                0o040666 (0x41b6) = S_IFDIR with 0666, for a directory
              i.e. a file appears mode 000 and a directory appears mode 666. A client that
              checks permission bits before reading will refuse every track.
  type      = 1 (NFREG) for files, 2 (NFDIR) for directories, matching mode.
  size      = the true byte size for a file; ALWAYS 0 for a directory.
  blocks    = ceil(size/512) for a file (110 of 111 file samples; one sample differs by
              one block, so treat it as advisory); ALWAYS 1 for a directory.
  fileid    = a FAT-derived id, and it is ALWAYS the first 4 bytes of the filehandle that
              describes the object:
                GETATTR reply : fileid == first 4 bytes of the CALL handle   (14/14)
                LOOKUP  reply : fileid == first 4 bytes of the RETURNED handle (387/387)
                READ    reply : fileid == first 4 bytes of the CALL handle   (7884/7884)
